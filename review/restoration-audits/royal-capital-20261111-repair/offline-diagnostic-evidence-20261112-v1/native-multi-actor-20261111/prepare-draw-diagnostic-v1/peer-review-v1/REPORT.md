## Static blockers before execution

### B1 — The advertised per-Page deadline does not cover host waits

`P/run-diagnostic.mjs:84` awaits `/program`'s `response.body()` without `guard`, timeout or host deadline. The response wait at 76 resolves when response headers exist; a response may then never finish its body. In that case the runner never reaches its `finally` at 111. The logger watchdog is an iframe timer (`P/instrument.js:343`), may not even have been installed yet, and does not reject this host body wait. Even most guarded operations only race the fatal promise, not a 45-second host deadline. Export `frame().evaluate()` at runner 113 and Page close at 152 are also outside a host deadline.

This is a real static control-flow gap in PLAN's hard 45-second-per-Page claim (`P/PLAN.md:126–140`), not an observed hang. A host absolute case deadline should govern navigation/body/action/wait/export work, retain a bounded failure receipt and reach Page cleanup when the budget expires. Instrumentation's timer remains useful as a separate browser-side safeguard. The owner must still close Chrome/CLI and verify processes after the callable returns or fails.

### B2 — Response body buffering is not bounded by decoded-byte reservation

`P/resource-observer.mjs:40–45` reserves declared Content-Length, then fully materializes `response.body()`, then checks decoded length. It records Content-Encoding at 31 but does not reject or handle encoded delivery before reading. For a compressed response, declared transport length can be within the 8 MiB/32 MiB reservations while the decoded body buffered by Playwright exceeds them. Several pending bodies can be materialized before their post-read actual-total checks. Missing Content-Length is correctly refused, but that alone is not a strict decoded-memory bound.

This is a conditional budget gap, not evidence that the existing local adapter compressed these locked files. For this bounded local diagnostic, require identity/no content encoding and a consistent declared/frozen size before buffering, or use a genuinely bounded way to consume an already-existing response. Keep any refusal as partial failure. Do not describe a post-materialization check as preventing oversized decoded materialization.

### B3 — The factory wrapper changes the original async result boundary

`P/instrument.js:277–285` invokes `Live2DModel.from` once with the original receiver/arguments, but returns `promise.then(...)`, not the original Promise. This changes Promise identity and adds an assimilation/reaction boundary before the actual caller resumes. Normal loaded model value and rejection reason are forwarded, but PLAN's unqualified original-result preservation statement is stronger than this implementation.

For transparent observation, register a side observation reaction before returning the original Promise; consume the side chain's failures without replacing or rejecting the factory's original result. Actual source `S/public/pairing/model_resources.js:23` awaits that factory, so this is the real loader path, not unused helper code. No live timing effect was measured here.

### B4 — Diagnostic exceptions are not consistently separated from runtime calls/failure state

The mesh/draw sampling blocks generally catch their own observation errors. However, Core's timing read at `P/instrument.js:192`, successful-call append/metadata work at 195–199, factory `loadStart=context()` at 278, render-frame construction/context at 289, and timing-event append at 316 are outside a diagnostic try/catch boundary. A diagnostic failure before a Reflect call can prevent the original invocation; a diagnostic failure after Core succeeds can turn that successful SDK update into a throw before the SDK's following `loadParameters()` call. These conditions have not been exercised or observed with the default clock/logger.

Also, an exception from the original Core/draw/render call is propagated, but not consistently marked as a failed diagnostic capture. The render wrapper records `completed:false` at 296–308, while coverage only audits the four ready geometry milestones (`P/resource-observer.mjs:131–150`). If a runtime caller catches an original exception outside those milestones, no global pageerror is guaranteed and the capture can miss the required partial/failure classification. The observer should record/disable capture on an original-call failure and rethrow the same exception; it should never swallow that exception, substitute one from logging, retry the original, or call it twice.

Use no-throw diagnostic boundaries for all pre/post samples, with the single original invocation outside them. Setup that follows `browserContext.newPage()` currently also occurs before the per-Page try/finally (`P/run-diagnostic.mjs:43–72`); include observer/listener installation inside the owned Page lifetime so setup exceptions still close it. This is a conditional exception-safety/cleanup gap, not a claim of an already reproduced player bug.
