## Code findings

1. **Entry generation and music generation have the correct distinct jobs in the proposed normal path.** `S/public/player/player.js:303` increments the entry generation for every entered node. Candidate `P/proposal/public/player/player.js:171–186` captures music generation separately and does not pass entry-generation cancellation into `apply()`. `S/public/studio/music_player.js:69–78` chooses its own generation synchronously before resource preparation, then checks it before creating a source. Therefore an inherited successor can advance the story while the still-current music load finishes. Suppressing that load merely because `sameEntry` becomes false would be a regression; this candidate does not do that.

2. **Stop, replacement, return to the already-playing resource, and inherited continuation are statically accounted for.** Stop changes music generation, clears loading and disposes voices (`S/public/studio/music_player.js:119`; the actual UI invokes player Stop at `S/public/player/player.js:44,102–112`). Replacement changes music generation before its first await (`music_player.js:69–78`). Returning to the current resource while another resource loads clears loading, changes music generation and ramps the retained voice (`music_player.js:57–65`), preserving its sample source rather than calling `start()` again. Late success checks generation before `new MusicVoice`/`start` (`music_player.js:78–84`); stale prepare failure returns without throwing (`music_player.js:75`). No browser evidence for these new overlaps was produced by this review.

3. **Desired music state and audible music state deliberately diverge; there is no immediate contradictory state consumer found in this player.** Candidate `player.js:179` publishes the resource at submission. The old current voice remains until preparation completes (`S/public/studio/music_player.js:70–89`), so the new desired resource must not be described as PLAY/audibility. The candidate observes desired/current/loading separately (`candidate:180–186`). The continuous player's `state.bg_music` read is entry restoration (`S/public/player/player.js:143,160`), while its other occurrences are the two assignment sites (`174,378`); `publish()` does not export it as an audible-resource field (`82–88`). Thus this timing change does not itself prove a false audible display or a sample-clock reset. Its semantics still require explicit acceptance.

4. **Late failure is a real behavior change, already disclosed, rather than an ownership bug hidden by this review.** Current entry + current music request calls `fail()` (`candidate:199–207`), which logs the current node and stops (`S/public/player/player.js:97–104`). After an inherited successor has entered, the same music-generation rejection is logged with the original owner but does not stop the successor. If desired A fails while old O is current, desired A can remain while O continues; an inherited successor does not retry A. This follows directly from `candidate:179,200–207` and the component's failure branch at `music_player.js:75`. The policy avoids falsely attributing the old node's error to the current one, but does not reconstruct native error/retry policy. Root must decide whether continuing with logged failure is acceptable; runtime QA must expose desired/current/loading and the original owner. No claim of covered failure behavior is justified yet.

5. **Conditional observer exception-safety gap, not a demonstrated normal-runtime failure.** The SUBMITTED observation/serialization/logger runs before `pending.then(...)` is attached (`candidate:189` versus `194`). If it throws, `submitNodeMusic()` exits and leaves that apply promise without this rejection observer. Also the FAILED logger precedes `fail()` (`201–207`), so its exception skips stop/error delivery; the observer catch only logs the diagnostic failure. Finally, the ignored promise returned by `observed.catch(...)` can reject if its own terminal logger/serializer throws (`211–212`). This means the comment claiming to consume diagnostic/error-delivery failures is not an unconditional guarantee. The concrete production snapshot currently returns plain scalar fields (`S/public/studio/visual_frame_clock.js:57–61`), and no failing normal logger/snapshot was observed. Do not call this a reproduced unhandled rejection. Before relying on exception-isolated diagnostics, attach settlement handlers first and use a no-throw reporter with error delivery outside its failure path; the existing frame clock already separates reporting this way (`visual_frame_clock.js:62–66`). This is the only specific code-hardening issue found here, not evidence that Stop/replacement normally fails.

6. **The component still owns fades and the sample clock.** Candidate changes neither `MusicVoice.start/currentTime` (`S/public/studio/music_voice.js:21–27`) nor generation-controlled gain subscriptions (`S/public/studio/music_player.js:91–119`). An apply settlement is neither fade completion nor audible progress. The prototype does not make a current resource restart just because an inherited entry changes. A repeated explicit assignment to the same resource while it is still loading is different: `current` has not changed yet, so it starts a new music generation and shares the cached preparation promise (`music_player.js:29–42,57–78`). This last-request-wins case should be observed in a bounded mechanical check if it occurs in the selected real route; it is not statically proven equivalent to the native loader's policy.
